Part 1 / Chapter 1

Values, references and identity

Predict when changing one variable's object changes what another variable sees.

Lantern Desk is a small app that turns notes into documents. Mira opens the same draft in two panels. A title change in one panel appears in the other. Before calling it a bug, ask a better question: do both panels refer to the same draft?

A value is something JavaScript can use, such as the number 3, the string "draft", or an object. A variable is a named binding to a value. When you assign one object-valued variable to another, both bindings hold the same object value. The program does not make a second object. Changing a property through one name can affect every other place that refers to that object.

Two objects with equal-looking properties can still be different objects. With objects, === compares identity. With the strings and numbers used here, it compares values of the same type. JavaScript passes values into functions; passing an object value gives the function access to that same object. Reassigning a parameter does not reassign the caller's variable.

A picture to remember

Two claim tickets can point to one coat. Altering the coat changes what either ticket retrieves. Replacing one ticket with a ticket for a different coat leaves the other ticket alone.

Same object, different name

const a = { title: "Draft" };
const b = a;
const c = { title: "Draft" };
b.title = "Ready";
console.log(a.title, c.title); // Ready Draft
console.log(a === b, a === c);  // true false

What counts as evidence

b.title changing does not prove a change in shared inheritance. First determine whether a and b are the same object. Later you will see two genuinely different objects share a separate prototype.

Common mistake

"Objects are passed by reference" can imply a function can rebind the caller's variable. A function can mutate the object it receives, but local rebinding and mutation are different operations.

Try it

Predict the two titles if the write is c.title = "Ready". Draw a second object and put each arrow on the correct identity before running the example.

Knowledge check

Which identity does b refer to after const b = a?

The same object as a. Assignment does not clone an object.

Why does c keep its first title?

It refers to a separately created object.

A function assigns its parameter to {}. Did it replace the caller's object?

No. It changed only its local binding.

Takeaway

Check identity first. Shared state can come from aliases or from a shared prototype; those are different routes.

Part 1 / Chapter 2

Objects, keys and methods

Read object syntax and separate keys, values, and operations.

Lantern Desk stores a title and a display method. A user may choose the title. The app chooses the method. Both are properties, but the app should grant control over only the first one.

An object can have properties. Each property has a key and a value or accessor behavior. A key is a string or a symbol. Numeric bracket keys such as 7 normally become strings like "7". Dot syntax uses a literal name; brackets compute the key from an expression. A method is a function used as a property; calling it with obj.method() normally supplies obj as this for an ordinary function.

Arrays are objects with special behavior for index keys and length. They still have properties and inherit methods. Do not assume that data sitting in an array escaped security rules for objects. If your input contract says "list of strings," check that shape; accepting any object with numeric-looking keys changes the contract.

A picture to remember

A document cabinet has labelled drawers. The label and the contents are separate. Letting a visitor write a note for one drawer is different from letting them choose any label in the cabinet.

Dot and bracket access

const draft = {
  title: "Draft",
  label() { return this.title; }
};
const field = "title";
console.log(draft[field], draft.label());
console.log(draft.field); // undefined

What counts as evidence

A dynamic key is not automatically unsafe. A fixed allowlist mapping "title" to an approved write is different from accepting every key. Ask which keys the input can choose and which object receives them.

Common mistake

Values and keys have different security jobs. Restricting title length cannot prevent a user from choosing a dangerous key elsewhere.

Try it

Predict draft["label"] and draft["label"](). Say which expression retrieves a function and which calls it.

Knowledge check

What does draft[field] read?

The name stored in field; here it is title.

Is an array unrelated to object inheritance?

No. Arrays are objects with array behavior and a prototype chain.

Is every method defined directly on the object using it?

No. An object can call an inherited function as a method.

Takeaway

Treat untrusted keys as instructions about where data goes. Validate them separately from the data itself.

Part 1 / Chapter 3

Functions, scope and time

Follow data across a function call and tell local state from shared state.

Lantern Desk assigns each export a new options object, but loads a single defaults object once. A helper writes to both during development. Which state survives the next export?

A function groups instructions. A parameter names an argument received on a call. Scope says where names can be used. Variables declared inside a function generally have fresh bindings on each call. A variable outside a function can be read by several calls. A closure is a function that retains access to bindings from its surrounding code.

This matters for security because "new request" does not mean "new JavaScript process." A server can reuse loaded modules, objects, and built-in prototypes for many requests. An async function can pause and resume later; other work can occur in between. JavaScript executing one turn at a time does not make shared mutations safe across turns.

A picture to remember

Each guest gets a fresh order slip. The restaurant also has one shared menu board. Editing a slip affects one order; editing the board changes what later guests see.

A fresh call and an old object

const defaults = { paper: "A4" };
function render() {
  const job = { copyCount: 1 };
  return [job.copyCount, defaults.paper];
}
console.log(render()); // [1, "A4"]
defaults.paper = "Letter";
console.log(render()); // [1, "Letter"]

What counts as evidence

If a second request changes after the first, a persistent object is one explanation. Other candidates include sessions, caches, DB rows, and load-balancer routing. A reliable test needs controls to separate them.

Common mistake

const stops rebinding, not property writes. const defaults is still mutable unless the object itself is constrained.

Try it

Move defaults inside render and predict both results after removing the outside write. Then consider what happens if a returned job is stored in a module-level array.

Knowledge check

Does const freeze an object?

No. It prevents assigning a new value to that binding.

Can a closure read a binding after the outer function returns?

Yes, if the closure retains access to it.

Does one event loop make cross-request mutations impossible?

No. Requests can run at different times and see the same shared state.

Takeaway

Draw two timelines: when an object is created, and when each request or function can still reach it.
